# Phase 3.5 — Crew Tracking MVP

**Date:** 2026-05-16
**Predecessor tag:** `phase-3` (target — Phase 3 must ship first)
**Target ship tag:** `phase-3.5` (~2 weeks)
**Status:** approved design, ready for implementation plan

---

## Goal

Phone GPS (Android) and browser GPS (web opt-in) feed an authoritative crew-position store. The desktop console map shows live crew dots alongside the job pins it already renders. A clock-in/clock-out gate ensures tracking only happens during a shift.

Phase 3.5 is **not** on the audit's original roadmap — it's a new feature insertion between Phase 3 and Phase 4. Slotting after Phase 3 means location writes flow through the audit_flush worker for free (every report becomes a queryable audit row).

## Constraints (decided 2026-05-16)

1. **Mobile client:** the existing Android app under `android/com.guildofsmiths.trademesh`. ~8000 LOC of uncommitted scaffolding includes `LocationService` (foreground GPS service), `GeofenceManager`, `TimeTrackingViewModel` (clock-in/out), `CrewPresenceRepository` (data shape already matches our target). The Android side is mostly built — needs server wiring and a confirmed build/sign/install path.
2. **Web role: two-way.** The desktop portal is both the operator viewer (foreman watches dots) and an opt-in tracked client (web user shares browser location via a header toggle — useful for tablet-in-truck or foreman-on-site).
3. **MVP scope.** Latest-position only (no history table), no geofencing, no auto-status-change, no trail replay. These are Phase 3.6 candidates.
4. **Schedule: after Phase 3.** Phase 3 Slice 2 + 3 (audit-flush + email) must ship first so position reports can flow through the audit queue without rework.
5. **Web live updates: 15s polling for MVP.** Matches existing jobs pattern. WebSocket push deferred — when it lands, the polling layer can be removed without API changes.

## Architecture

```
        |  POST /api/presence/location          |  POST /api/presence/location
        |  every 60s while clocked in           |  every 60s while sharing
        v                                       v
                  +-------------------+
                  |  Express handler  |
                  |  shifts gate +    |
                  |  crewPositionSvc  |

                            |
              UPSERT into crew_positions   (latest only, 1 row per user)

                            |
                +-----------+-------------+
                |                         |
[ Desktop console map ]          (future Phase 4)
  polls GET /api/crew/positions    WS broadcast on update
  every 15s; renders dots distinct from job pins
```

### Data model — migration 010

```sql
CREATE TABLE shifts (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     TEXT NOT NULL REFERENCES profiles(id),
  started_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  ended_at    TIMESTAMPTZ,
  source      TEXT NOT NULL  -- 'android' | 'web' | 'admin'
);

-- Partial unique index: at most one open shift per user.
CREATE UNIQUE INDEX shifts_one_open_per_user_uidx
  ON shifts (user_id)
  WHERE ended_at IS NULL;

CREATE INDEX shifts_user_started_idx ON shifts (user_id, started_at DESC);

CREATE TABLE crew_positions (
  user_id        TEXT PRIMARY KEY REFERENCES profiles(id),
  latitude       DOUBLE PRECISION NOT NULL,
  longitude      DOUBLE PRECISION NOT NULL,
  accuracy_m     REAL,
  recorded_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  source         TEXT NOT NULL,
  battery_pct    INTEGER
);
```

The partial unique index on `shifts(user_id) WHERE ended_at IS NULL` makes "user already has an open shift" structurally impossible. `crew_positions` has user_id as PK (one row per user, UPSERT on update).

### Endpoints

| Route | Auth | Body | Notes |
|---|---|---|---|
| `POST /api/shifts/start` | requireAuth | `{source}` | Inserts open shift; 409 if already open |
| `POST /api/shifts/end`   | requireAuth | `{}`        | Sets `ended_at` on open shift; 404 if none |
| `GET /api/shifts/current` | requireAuth | — | Returns caller's open shift or `null` |
| `POST /api/presence/location` | requireAuth | `{lat, lng, accuracy_m?, battery_pct?}` | UPSERT `crew_positions`; 403 if no open shift |
| `GET /api/crew/positions` | requireForemanRole | — | All positions where user has open shift |

All audited via `auditLog.log()` — Slice 1 emits actions `SHIFT_STARTED`, `SHIFT_ENDED`, `LOCATION_REPORTED`. After Phase 3 Slice 2 ships, those flow through the audit_flush worker (no app code change — the API of `auditLog.log()` is what changes; callers are already async-clean).

### Android wiring (Slice 2)

Existing modules to plug in (do NOT rewrite):
- `LocationService.kt` (207 LOC) — foreground service, already starts/stops via TimeTracking
- `TimeTrackingViewModel.kt` (748 LOC) — clock-in/out flow, already manages OkHttp + baseUrl
- `CrewPresenceRepository.kt` — data class already has `latitude/longitude/accuracyMeters/locationSharingEnabled`
- `GeofenceManager.kt` (454 LOC) — geofencing exists but stays inert for MVP

Changes:

- `TimeTrackingViewModel.clockIn()` → `POST /api/shifts/start`. Stores `shift_id` in memory; clock-out calls `/api/shifts/end`.
- `LocationService.onLocationChanged(...)` callback → POST `/api/presence/location` every 60s. The existing local writes to `CrewPresenceRepository` stay (used for the in-app crew list).
- App must build, sign, install. Status is unknown — first task in Slice 2 is `./gradlew assembleDebug`. If it fails, plan adapts to "fix the build first, track second."

## Risks

1. **Android build state unknown.** Mitigation: Slice 2 Task 0 is build-or-bust. If it takes >1 day, escalate; consider falling back to a small PWA tracker as a stopgap.
2. **Backend port mismatch.** Hardcoded `:3002` in `TimeTrackingViewModel`. Slice 2 fixes via `BuildConfig`.
3. **Web browser background location.** Mobile Safari stops emitting when tab is backgrounded. Two-way web works best on laptops, less reliably on phones-as-browsers.
4. **Two clients, one contract.** Android and Web hit the same `/api/presence/location`. Backend tests are the source of truth; client tests don't need to mirror.
5. **Privacy.** Tracking only happens during an open shift. Server enforces. No history table yet limits the privacy surface.

## Done criteria

- Mobile shift start (Android or Web) → 60s later, position visible on the desktop map
- Web opt-in toggle in header → same flow works from browser
- Clock out from any client → dot disappears within the 15s polling interval
- All backend tests pass against real pg
- Android tested on at least one device (emulator OK)
- `OPERATIONS.md` updated with shifts/positions retention notes
- All three slices tagged; `phase-3.5` annotated tag exists

## What Phase 3.5 does NOT do

- No history / trail / replay. Phase 3.6.
- No geofencing or auto-status-change on arrival. Phase 3.6.
- No WebSocket push for map updates. Phase 4 (after queueWatcherDaemon).
- No dispatch ("nearest crew to this job"). Phase 4+.
- No admin-set remote clock-in (admin can clock OUT a stuck user but cannot clock someone IN). Phase 4 if needed.
- No analytics / hours-worked rollups. The shifts table supports this, but the UI doesn't.
