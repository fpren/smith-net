# Phase 3.5 Slice 2 — Android wiring

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Point the existing Android `LocationService` and `TimeTrackingViewModel` at the Slice 1 backend so phone GPS lands in `crew_positions` while clocked in. Largely a wiring slice — the Kotlin location infrastructure is already built (LocationService 207 LOC, TimeTrackingViewModel 748 LOC, GeofenceManager 454 LOC, CrewPresenceRepository with `latitude/longitude/accuracyMeters` fields).

**Architecture:** Add a `PresenceApiClient` that wraps OkHttp for three calls (`POST /api/shifts/start`, `POST /api/shifts/end`, `POST /api/presence/location`). Wire `TimeTrackingViewModel.clockIn()` to call shifts/start (and persist the returned shift id). Wire `LocationService.onLocationChanged(...)` to POST every emission to `/api/presence/location`. Move the hardcoded backend URL from `http://10.0.2.2:3002` into a `BuildConfig.BACKEND_URL` (dev = emulator-localhost on the api port, prod = Hetzner).

**Tech Stack:** Kotlin + Android SDK + OkHttp 4.x (already a dep) + AGP/Gradle. JWT cookie is reused from the existing auth flow.

**Prerequisites:**
- Phase 3.5 Slice 1 shipped (tag `phase-3.5-slice-1`, commit `81a24ae`). Backend endpoints live and return 200/201/403 correctly.
- Register fix `771d4dc` landed so register auto-creates the profile row.
- Android source at `android/com.guildofsmiths.trademesh`. Permissions already in `AndroidManifest.xml`: `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `ACCESS_BACKGROUND_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`. `LocationService` declared with `foregroundServiceType="location"`.
- Local Android SDK available (`local.properties` exists at `android/local.properties`).
- Working branch `feat/relay-hetzner-postgres`.

**Reference docs:**
- Spec: `docs/superpowers/specs/2026-05-16-phase-3.5-crew-tracking-mvp-design.md`
- Slice 1 plan (backend): `docs/superpowers/plans/2026-05-16-phase-3.5-slice-1-backend.md`

- [ ] **Step 2: Implement PresenceApiClient**

Create `android/app/src/main/java/com/guildofsmiths/trademesh/data/PresenceApiClient.kt`:

```kotlin
package com.guildofsmiths.trademesh.data

import android.util.Log
import com.guildofsmiths.trademesh.BuildConfig
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext
import okhttp3.MediaType.Companion.toMediaType
import okhttp3.OkHttpClient
import okhttp3.Request
import okhttp3.RequestBody.Companion.toRequestBody
import org.json.JSONObject
import java.io.IOException

/**
 * Phase 3.5 Slice 2: thin OkHttp wrapper for the crew-tracking backend.
 *
 * Endpoints:
 *   POST /api/shifts/start   { source: "android" }
 *   POST /api/shifts/end
 *   POST /api/presence/location { lat, lng, accuracy_m?, battery_pct? }
 *
 * Caller is responsible for owning a CookieJar so the auth cookie persists
 * across requests. Pass the configured OkHttpClient via the constructor.
 */
class PresenceApiClient(private val client: OkHttpClient) {

    companion object {
        private const val TAG = "PresenceApiClient"
        private val JSON = "application/json; charset=utf-8".toMediaType()
    }

    private val baseUrl: String get() = BuildConfig.BACKEND_URL

    /** Returns the shift id (UUID string) on success; throws on 4xx/5xx. */
    suspend fun startShift(source: String = "android"): String = withContext(Dispatchers.IO) {
        val body = JSONObject().put("source", source).toString().toRequestBody(JSON)
        val req = Request.Builder().url("$baseUrl/api/shifts/start").post(body).build()
        client.newCall(req).execute().use { res ->
            if (!res.isSuccessful) throw IOException("startShift HTTP ${res.code}")
            val json = JSONObject(res.body?.string() ?: "{}")
            json.getString("id")
        }
    }

    /** No-op on 404 (no open shift). Throws on other 4xx/5xx. */
    suspend fun endShift() = withContext(Dispatchers.IO) {
        val req = Request.Builder()
            .url("$baseUrl/api/shifts/end")
            .post("".toRequestBody(JSON))
            .build()
        client.newCall(req).execute().use { res ->
            if (res.code == 404) return@withContext  // already off-clock
            if (!res.isSuccessful) throw IOException("endShift HTTP ${res.code}")
        }
    }

    /** POST a location report. 403 means "no open shift" — caller should stop the service. */
    suspend fun postLocation(
        lat: Double,
        lng: Double,
        accuracyM: Float? = null,
        batteryPct: Int? = null,
    ): Boolean = withContext(Dispatchers.IO) {
        val payload = JSONObject().apply {
            put("lat", lat)
            put("lng", lng)
            if (accuracyM != null) put("accuracy_m", accuracyM)
            if (batteryPct != null) put("battery_pct", batteryPct)
        }
        val req = Request.Builder()
            .url("$baseUrl/api/presence/location")
            .post(payload.toString().toRequestBody(JSON))
            .build()
        client.newCall(req).execute().use { res ->
            if (res.code == 403) {
                Log.w(TAG, "postLocation 403 — no open shift; caller should stop tracking")
                return@withContext false
            }
            if (!res.isSuccessful) throw IOException("postLocation HTTP ${res.code}")
            true
        }
    }
}
```

The `withContext(Dispatchers.IO)` keeps these calls off the main thread. Calls are `suspend` — callers run them in coroutine scopes (which both LocationService and TimeTrackingViewModel already use).

- [ ] **Step 3: Post location every 60s inside onLocationChanged**

Find `onLocationChanged(location: Location)`. Add a debounced POST:

```kotlin
override fun onLocationChanged(location: Location) {
    // ... existing local writes (CrewPresenceRepository, LocationTrailRepository)

    val now = System.currentTimeMillis()
    if (now - lastPostAtMs < postIntervalMs) return
    lastPostAtMs = now

    val accuracy = if (location.hasAccuracy()) location.accuracy else null
    val battery = readBatteryPct()  // helper — implement below if not already present

    serviceScope.launch {
        try {
            val ok = presenceApi.postLocation(
                lat = location.latitude,
                lng = location.longitude,
                accuracyM = accuracy,
                batteryPct = battery,
            )
            if (!ok) {
                Log.w(TAG, "postLocation returned no-open-shift; stopping service")
                stopSelf()  // server says we're not clocked in — stop tracking
            }
        } catch (e: Exception) {
            Log.w(TAG, "postLocation failed (will retry on next emission): ${e.message}")
        }
    }
}
```

If `readBatteryPct()` doesn't exist, add a private helper:

```kotlin
private fun readBatteryPct(): Int? {
    return try {
        val bm = getSystemService(Context.BATTERY_SERVICE) as android.os.BatteryManager
        bm.getIntProperty(android.os.BatteryManager.BATTERY_PROPERTY_CAPACITY)
    } catch (e: Exception) {
        null
    }
}
```

## What slice 2 did NOT do

- No iOS client. (PWA on iOS Safari could be a Phase 3.6 stopgap.)
- No background-location power optimization beyond the 60s debounce. FusedLocationProvider may be a better fit than the raw LocationManager — Phase 3.6 if battery becomes an issue.
- No retry queue for failed location posts. A 5xx today drops the report; next emission tries fresh. Acceptable for MVP (UPSERT means we only ever care about the latest).
- No auth flow inside the Android app from scratch — relies on whatever auth the app already has wired. If that auth flow is broken or absent, smoke step 3 deferred.
- No cookie-jar normalization between LocationService's local OkHttpClient and the shared app one. If 401s appear, follow up by passing the shared client into PresenceApiClient.

Slice 3 (web view + opt-in toggle + closeout) follows.
