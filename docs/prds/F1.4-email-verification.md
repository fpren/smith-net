# F1.4 — Email verification on signup

| Field | Value |
|---|---|
| Pitch | 1 — Auth security hardening |
| Cycle | 1 |
| Appetite | 4 days |
| Owner | backend + Android UI |
| Dependencies | F1.1, F1.2, F1.3 |
| Closes blocker | S6 |

---

## 1. Problem

Anyone can register with any email; no proof of ownership. Risks:
- Spam accounts skew metrics
- Founder seats can be claimed by burner addresses
- Future password reset depends on email — but unverified email = unrecoverable account

## 2. Goal

After this PRD: new users must verify email before they can:
- Start any trial (locks founder seats)
- Generate / send invoices (passive distribution surface)
- Receive any push notification

Pre-existing users (registered before this PRD): grandfathered to "verified" automatically.

## 3. Non-goals

- Phone verification (post-launch)
- 2FA (post-launch)
- Re-verification on email change (defer; rarely changed)

## 4. Design

### 4.1 Schema

Migration `004b_email_verification.sql`:

```sql
ALTER TABLE profiles
  ADD COLUMN IF NOT EXISTS email_verified_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS email_verification_token TEXT,
  ADD COLUMN IF NOT EXISTS email_verification_expires_at TIMESTAMPTZ;

-- Backfill existing users
UPDATE profiles SET email_verified_at = NOW() WHERE email_verified_at IS NULL;
```

### 4.2 Email send

Using existing `nodemailer` (or add it). SMTP creds from env:
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`
- `MAIL_FROM=Smith Net <noreply@smithnet.app>`

Email template (verification.html):

```
SUBJECT: Verify your Smith Net email

Hey ${displayName},

Tap to verify your email and finish setting up Smith Net:

https://app.smithnet.app/verify?token=${token}

This link expires in 24 hours.

— Smith Net (smithnet.app)
```

### 4.3 Endpoints

```typescript
// On registration:
POST /api/auth/register
// ... existing ...
// After insert, generate token, store in email_verification_token, email_verification_expires_at = NOW + 24h
// Send email
// Response: 201 + { user, accessToken, refreshToken, requiresEmailVerification: true }

// New endpoint:
GET /api/auth/verify?token=:token
// Look up profile WHERE email_verification_token = $1 AND email_verification_expires_at > NOW()
// If found: SET email_verified_at = NOW(), email_verification_token = NULL
// Redirect to a /verified.html page (server-rendered) that says "Email verified! Return to the app."
// If not found: render /verify-failed.html

// New endpoint:
POST /api/auth/resend-verification
// Authenticated. If !email_verified_at, generate new token + resend.
// Rate-limited: 1 per minute
```

### 4.4 Enforcement middleware

```typescript
// backend/src/auth.ts
export function requireVerifiedEmail(req: AuthenticatedRequest, res: Response, next: NextFunction) {
  if (!req.user!.email_verified_at) {
    return res.status(403).json({
      error: 'Email not verified',
      code: 'email_not_verified',
    });
  }
  next();
}
```

Apply to gated routes:
- `POST /api/me/start-trial` (F7.1 dependency)
- `POST /api/invoices/:id/send`
- `POST /api/proposals/:id/send`

NOT applied to: read-only endpoints, basic CRUD, channel/messaging — let unverified users explore the app, just not commit to public actions.

### 4.5 Client UX

Android `WelcomeToOpenScreen` (A4) — if `requiresEmailVerification`:
- Add a banner near top: `EMAIL VERIFICATION SENT — CHECK ${email}`
- Add `[ Resend email ]` text-link
- Trial-start button shows: `[ START SOLO TRIAL — VERIFY EMAIL FIRST ]` (disabled until verified)

Once verified (via deep link OR client polls `/api/me`):
- Banner disappears
- Trial-start CTA enables

## 5. Acceptance criteria

| AC | Description | Verification |
|---|---|---|
| AC-1 | Registration sends verification email within 5s | E2E |
| AC-2 | Email contains link with valid token | Email assertion |
| AC-3 | Tapping link → GET /api/auth/verify → marks email_verified_at | DB assertion |
| AC-4 | Verified link redirects to /verified.html success page | E2E |
| AC-5 | Expired token → /verify-failed.html with "Token expired" + resend prompt | E2E |
| AC-6 | Reused token → /verify-failed.html with "Already used" message | E2E |
| AC-7 | POST /api/me/start-trial without verified email → 403 email_not_verified | API test |
| AC-8 | POST /api/invoices/:id/send without verified email → 403 email_not_verified | API test |
| AC-9 | POST /api/auth/resend-verification → email sent; rate-limited 1/min | API test |
| AC-10 | Existing users (grandfathered) have email_verified_at NOT NULL | Migration test |
| AC-11 | Android shows verification banner on A4 if not yet verified | UI test |
| AC-12 | Android polls /api/me every 30s while on A4 to detect verification | UI test |

## 6. BDD scenarios

```gherkin
Feature: Email verification on signup

Scenario: New user registers, receives verification email
  When POST /api/auth/register with email "alice@example.com" and valid password
  Then the response is 201 with requiresEmailVerification: true
  And profile.email_verification_token is set
  And profile.email_verification_expires_at is NOW + 24 hours
  And profile.email_verified_at is NULL
  And a verification email is sent to alice@example.com within 5s

Scenario: User verifies via email link
  Given a profile with token "abc123"
  When GET /api/auth/verify?token=abc123 arrives
  Then profile.email_verified_at is set to NOW
  And profile.email_verification_token is NULL
  And the response is a 200 HTML redirect to /verified.html

Scenario: Expired token rejected
  Given a profile with token "expired1" and expires_at in the past
  When GET /api/auth/verify?token=expired1
  Then the response renders /verify-failed.html
  And the page shows "Token expired" with a "Resend" link

Scenario: Verified user can start trial
  Given an unverified user
  When they POST /api/me/start-trial { targetTier: "solo" }
  Then the response is 403 email_not_verified
  When they verify via email link
  And they retry POST /api/me/start-trial
  Then the response is 200 and trial is created

Scenario: Resend verification email is rate-limited
  Given a user with unverified email
  When they POST /api/auth/resend-verification
  Then a new email is sent
  When they POST /api/auth/resend-verification again within 60s
  Then the response is 429 with retry_after_seconds
```

## 7. Edge cases

| Case | Behavior |
|---|---|
| User registers with typo'd email | They never receive link; resend won't help; they must re-register with correct email (or contact support) |
| Email provider blocks verification email as spam | User can request resend; we monitor delivery rates |
| User opens verification link in different browser session | Works — token is in URL, no session needed |
| User clicks verification link twice | Second click → "Already verified" success page |
| User registers, verifies, deletes account, re-registers same email | Treated as new account; new token issued |
| Hetzner mail relay down | Registration still succeeds; verification email queued for retry; user sees banner with retry button |

## 9. Telemetry

- New audit: `EMAIL_VERIFIED` action
- Metric: time-to-verify median (target: < 10 min for users who do verify)
- Metric: % of registrations that verify within 24h (target: > 70%)
- Alert: if SMTP failure rate > 5%

## 10. Risk

| Risk | Mitigation |
|---|---|
| Email deliverability (spam folders) | Set up SPF + DKIM + DMARC for `smithnet.app` domain in DNS |
| Verification step adds friction → conversion drop | Accept the trade-off; only blocks public actions, not exploration |
| User registers but never verifies | Account remains in unverified state; cleanup cron deletes after 30 days of no-verification |
