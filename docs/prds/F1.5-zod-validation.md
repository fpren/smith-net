# F1.5 — Zod schema validation at every endpoint

| Field | Value |
|---|---|
| Pitch | 1 — Auth security hardening |
| Cycle | 1 |
| Appetite | 5 days |
| Owner | backend |
| Dependencies | F1.1 (auth middleware established) |
| Closes blocker | B15, S7 |

---

## 1. Problem

Most endpoints validate body fields ad-hoc:

```typescript
if (!email || !password || !displayName) return res.status(400).json({ error: '...' });
```

This:
- Misses type coercion attacks (e.g., `email: { $ne: null }`)
- Lacks schema documentation (the contract is hidden in the handler)
- Creates inconsistent error responses
- Allows mass-assignment when handlers spread `req.body`

## 2. Goal

After this PRD: every endpoint with a body uses **`zod`** to:
1. Validate body shape (reject extras unless explicitly allowed)
2. Coerce types safely (no string-where-number pollution)
3. Return consistent error shape `{ error: 'validation', code: 'validation', details: {...} }`
4. Schemas are exportable for client TypeScript codegen (future)

## 3. Non-goals

- Replacing Express with another framework
- Auto-generating OpenAPI / Swagger from zod (deferred)
- Migrating Android client to consume zod schemas (separate later)
- Validating WebSocket message shapes (separate PRD if needed)

### 4.2 Validation middleware

```typescript
// backend/src/middleware/validate.ts
import { z, ZodSchema } from 'zod';
import { Request, Response, NextFunction } from 'express';

export function validateBody<T extends ZodSchema>(schema: T) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({
        error: 'Validation failed',
        code: 'validation',
        details: result.error.flatten(),
      });
    }
    req.body = result.data; // safe-parsed data replaces raw
    next();
  };
}

export function validateQuery<T extends ZodSchema>(schema: T) { /* ... */ }
export function validateParams<T extends ZodSchema>(schema: T) { /* ... */ }
```

### 4.3 Schema definitions

Create `backend/src/schemas/` with one file per domain:

```typescript
// backend/src/schemas/auth.ts
import { z } from 'zod';

export const RegisterBody = z.object({
  email: z.string().email().toLowerCase(),
  password: z.string().min(8).max(200),
  displayName: z.string().min(1).max(100).trim(),
}).strict();

export const LoginBody = z.object({
  email: z.string().email().toLowerCase(),
  password: z.string(),
}).strict();

export const RefreshBody = z.object({
  refreshToken: z.string().min(1),
}).strict();
```

```typescript
// backend/src/schemas/jobs.ts
import { z } from 'zod';

export const CreateJobBody = z.object({
  title: z.string().min(1).max(200),
  description: z.string().max(5000).optional(),
  clientName: z.string().max(200).optional(),
  clientEmail: z.string().email().optional(),
  clientPhone: z.string().max(50).optional(),
  location: z.string().max(500).optional(),
  trade: z.string().max(100).optional(),
  status: z.enum(['backlog', 'todo', 'in_progress', 'review', 'done', 'archived']).optional(),
  priority: z.enum(['low', 'medium', 'high', 'urgent']).optional(),
  dueDate: z.coerce.date().optional(),
  estimatedHours: z.number().nonnegative().optional(),
  budget: z.number().nonnegative().optional(),
}).strict();

export const PatchJobBody = CreateJobBody.partial();

export const JobListQuery = z.object({
  status: z.enum(['backlog', 'todo', 'in_progress', 'review', 'done', 'archived']).optional(),
  assignedTo: z.string().uuid().optional(),
});
```

(Repeat for: intents, synthesis, ledger, channels, messages, time-entries, expenses, materials, proposals, invoices, reports, telemetry, founder-seats, subscription, etc.)

### 4.4 Apply to routes

```typescript
// backend/src/authRoutes.ts
import { validateBody } from './middleware/validate';
import { RegisterBody, LoginBody, RefreshBody } from './schemas/auth';

authRouter.post('/register', validateBody(RegisterBody), async (req, res) => {
  const { email, password, displayName } = req.body; // already validated + typed
  // ... existing logic, simplified ...
});
```

### 4.5 Strict mode (`.strict()`)

Most schemas use `.strict()` — rejects unknown fields. Prevents mass-assignment:

```
POST /api/jobs { title: "X", role: "admin" }  ← role would be ignored before; now rejects with validation error
```

When PATCH endpoints need partial updates, use `.partial()` (which inherits strict).

### 4.6 Per-request body size limit

Already exists (`express.json()` with default 100kb). Add explicit limit for clarity:

```typescript
app.use(express.json({ limit: '512kb' }));
```

## 5. Acceptance criteria

| AC | Description | Verification |
|---|---|---|
| AC-1 | Every authenticated POST/PATCH endpoint has a zod schema | grep + audit |
| AC-2 | POST /api/auth/register with `{password: { $ne: null }}` (NoSQL-injection probe) → 400 validation | API test |
| AC-3 | POST /api/jobs with extra field `role: 'admin'` → 400 validation (strict mode) | API test |
| AC-4 | Validation errors return shape `{ error, code: 'validation', details }` | Format assertion |
| AC-5 | Type coercion: `dueDate: "2026-05-30"` (string) coerces to Date | Validation test |
| AC-6 | Body size > 512kb → 413 payload too large | API test |
| AC-7 | All existing API tests still pass after schema rollout | Regression |
| AC-8 | TypeScript compilation succeeds with `req.body` types narrowed by `z.infer` | tsc check |
| AC-9 | Schemas exported from `backend/src/schemas/` index for future client codegen | grep |

## 6. BDD scenarios

```gherkin
Feature: Zod validation at every endpoint

Scenario: Strict mode rejects unknown fields
  When POST /api/jobs with body {"title": "X", "secret_admin_field": true}
  And valid auth
  Then the response is 400
  And the body is {"error": "Validation failed", "code": "validation", "details": {...}}
  And no job is created

Scenario: Email coerced to lowercase
  When POST /api/auth/register with email "Alice@EXAMPLE.com"
  Then the stored profile.email is "alice@example.com"

Scenario: NoSQL-style injection blocked
  When POST /api/auth/login with body {"email": "alice@x.com", "password": {"$ne": null}}
  Then the response is 400 validation
  And no login attempt is made

Scenario: Number field rejects string
  When POST /api/jobs with {"title": "X", "estimatedHours": "ten"}
  Then the response is 400 validation with details mentioning estimatedHours

Scenario: Partial PATCH with valid subset succeeds
  When PATCH /api/jobs/:id with body {"description": "updated"}
  Then the response is 200 and only description is updated

Scenario: Body size limit enforced
  When POST /api/jobs with body of 600kb
  Then the response is 413 payload too large
```

## 7. Edge cases

| Case | Behavior |
|---|---|
| Field is allowed-empty-string vs allowed-null vs allowed-undefined | Each schema explicit per field. Document in JSDoc. |
| Date coercion fails (bad ISO format) | 400 validation with helpful "expected ISO date" |
| Backward-compat: existing client sending an extra field | strict-mode rejects; if known to be sent by old client, schema must add `.passthrough()` (rare) or whitelist that field |
| Nested objects | zod handles natively; document union types as needed |
| Array fields | `z.array(z.string()).max(100)` — bound array size |

## 10. Telemetry

- New metric: `validation_failure_count_per_endpoint_per_day` — alert if any endpoint exceeds 1000/day (probable client bug or attack)
- Audit: bumping `SECURITY_ALERT` if validation rejects suspicious patterns (e.g., NoSQL-injection probes)

## 11. Risk

| Risk | Mitigation |
|---|---|
| Strict mode breaks an existing client sending extra fields | Per-endpoint audit; whitelist if needed; preferably fix client to not send extras |
| Schema drift between client (Android) and server | Future codegen step (out of scope this PRD); for now, manual sync via PR review |
| Performance overhead of zod parsing | Negligible (~0.1ms per request); reject-early model is faster than processing bad data |
