# F1.1 — Remove `X-User-Id` "simplified auth" header

| Field | Value |
|---|---|
| Pitch | 1 — Auth security hardening |
| Cycle | 1 |
| Appetite | 3 days |
| Owner | backend |
| Dependencies | none (this is the first PRD) |
| Closes blocker | B1, S1 (Critical) |
| Closes gap | G1 (Critical) |

---

## 1. Problem

Several `apiRouter` endpoints (`backend/src/api.ts`) read user identity from `req.headers['x-user-id']` as "simplified auth" — bypassing the real JWT middleware. **Any client can spoof any user.** Cannot publicly launch.

Affected endpoints (verified by grep `'x-user-id'` and `X-User-Id`):
- `POST /api/channels` — `creatorId = req.headers['x-user-id'] as string || 'anonymous'`
- (and others — see PR scope below)

## 2. Goal

Replace `X-User-Id` parsing with `authenticateToken` middleware on every authenticated route. After this PRD: no route reads from `X-User-Id` or `X-User-Name` headers. `req.user` is the only identity source.

## 3. Non-goals

- Adding new auth methods (OAuth, magic links) — that's post-launch
- Replacing JWT scheme — HS256 stays
- Touching `/p/:uuid`, `/i/:uuid`, `/api/health` (intentionally public — no auth)

## 4. Design

### 4.1 Audit phase (day 1)

Run `grep -rn "x-user-id\|X-User-Id\|x-user-name\|X-User-Name" backend/src/` and produce a complete list of affected files + lines. Flag in PR description.

### 4.2 Middleware enforcement (day 2)

```typescript
// backend/src/api.ts
import { authenticateToken } from './auth';

// Apply to all /api/* below — except for explicitly allowlisted public sub-routes
apiRouter.use(authenticateToken);

// Already-authed sub-routers like /api/admin (which uses requireRole) layer on top.
```

Existing `/api/auth/{register,login,refresh}` already mounted with their own `authLimiter` BEFORE `apiRouter` — they remain unauthenticated by design.

### 4.3 Per-endpoint identity refactor (day 2-3)

For each `req.headers['x-user-id'] as string || 'anonymous'` callsite:

```typescript
// BEFORE
const creatorId = req.headers['x-user-id'] as string || 'anonymous';

// AFTER
const creatorId = (req as AuthenticatedRequest).user!.id;
```

Use the `AuthenticatedRequest` type from `auth.ts`. Remove the `|| 'anonymous'` fallback — `authenticateToken` would have rejected before reaching here.

### 4.4 Deprecation guard (day 3)

For one release window, log a WARNING when `X-User-Id` headers are present even if not used:

```typescript
app.use((req, res, next) => {
  if (req.headers['x-user-id'] || req.headers['x-user-name']) {
    console.warn('[deprecated-header]', req.path, 'received X-User-Id; this will be removed', {
      ip: req.ip, ua: req.get('user-agent'),
    });
  }
  next();
});
```

Remove this guard in a follow-up PR after one release window confirms no client still sends them.

## 6. Acceptance criteria

| AC | Description | Verification |
|---|---|---|
| AC-1 | `grep -rn "x-user-id\|X-User-Id" backend/src/` returns 0 production matches (deprecation guard string excluded) | grep |

| AC-7 | Deprecation warning logs when `X-User-Id` header present in any request | log assertion |
| AC-8 | All existing API contract tests pass after refactor | regression suite |

## 7. BDD scenarios

```gherkin
Feature: All authenticated routes require JWT, not X-User-Id

Scenario: Request to /api/channels without Authorization fails
  When a POST to /api/channels with body {name: "test", type: "group"} arrives
  And the request has NO Authorization header
  Then the response is 401 unauthenticated
  And no channel is created

Scenario: Request with X-User-Id but no Authorization fails
  When a POST to /api/channels arrives with header X-User-Id: "spoofed-uid"
  And no Authorization header
  Then the response is 401 unauthenticated
  And no channel is created
  And a [deprecated-header] warning is logged

Scenario: Request with valid Authorization succeeds
  Given a valid JWT for user "alice"
  When a POST to /api/channels arrives with that Authorization header
  Then the response is 201
  And the channel's creator_id equals alice's userId
  And req.user.id equals alice's userId

Scenario: Request with both X-User-Id (spoofed) and valid Authorization (real)
  Given a valid JWT for user "alice"
  When a POST to /api/channels arrives with X-User-Id: "bob" and Authorization for alice
  Then the response is 201
  And the channel's creator_id equals alice's userId (NOT "bob")
  And the X-User-Id header is ignored
  And a [deprecated-header] warning is logged
```

## 8. Edge cases

| Case | Behavior |
|---|---|
| Existing Android client still sends `X-User-Id` | Header logged as deprecated; ignored. Client must already be sending Authorization (it does — `ChatManager` uses backend with auth). Behavior unchanged. |
| Public route (`/api/health`) called with Authorization | Token ignored; endpoint serves response normally |
| Admin route (`/api/admin/*`) | Existing `requireRole(ADMIN)` layered on top of `authenticateToken` — still works |
| Webhook routes (future, e.g. `/webhooks/stripe`) | Webhook routes will be exempt from `authenticateToken` and use their own signature verification — handled in F3.1 |
| Public proposal/invoice pages (`/p/:uuid`, `/i/:uuid`) | Mounted via `proposalPublicRouter`, NOT `apiRouter` — unaffected by this change |

## 12. Risk

| Risk | Mitigation |
|---|---|
| Existing Android build talks to backend with `X-User-Id` only (rare; should always have Authorization) | Deprecation guard logs but doesn't reject. After 1 release window with no warnings, hard-remove. |
| Deprecation guard floods logs in production | Sample log to 1% of warnings if volume exceeds 100/min |
| Admin route inadvertently broken | Existing `requireRole` middleware ordering preserved |
