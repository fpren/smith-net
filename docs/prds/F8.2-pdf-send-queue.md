# F8.2 — PDF send queue + month-end cron

| Field | Value |
|---|---|
| Pitch | 8 — Branded PDF stamp + send queue |
| Cycle | 3 |
| Appetite | 2 days |
| Owner | backend |
| Dependencies | F6.1 (cap enforcement), F8.1 (branding), F2.2 (entitlements) |

---

## 1. Problem

When Free user hits 6th-PDF cap and dismisses the upgrade overlay, they tap "Next month: in X days" — the draft must be queued and auto-sent on day 1 of next month, with branding stamp applied at that send time. Without this, users lose work.

## 2. Goal

After this PRD: a `pending_sends` table queues over-cap sends; cron flushes the queue on month rollover (after the F6.1 monthly counter reset).

## 3. Design

### 3.1 Migration M9

```sql
-- 011_create_pending_sends_table.sql
BEGIN;

CREATE TABLE IF NOT EXISTS pending_sends (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  profile_id TEXT NOT NULL REFERENCES profiles(id),
  send_kind TEXT NOT NULL CHECK (send_kind IN ('invoice', 'proposal')),
  source_id UUID NOT NULL,           -- invoices.id OR proposals.id
  scheduled_for TIMESTAMPTZ NOT NULL, -- next month day-1
  attempts INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'queued'
    CHECK (status IN ('queued', 'sent', 'failed', 'canceled')),
  last_error TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_pending_sends_status_scheduled
  ON pending_sends(status, scheduled_for)
  WHERE status = 'queued';

CREATE INDEX IF NOT EXISTS idx_pending_sends_profile
  ON pending_sends(profile_id);

COMMIT;
```

### 3.2 Modify F6.1's PDF send handler

```typescript
// In POST /api/invoices/:id/send — instead of returning bare 403, allow queue option
apiRouter.post('/invoices/:id/send', validateBody(SendBody), async (req, res) => {
  const profileId = req.user!.id;
  const ent = await resolveTier(profileId);
  const cap = ent.caps.pdfSendsPerMonth;
  const current = await getCurrentPdfSends(profileId);

  if (cap !== 'unlimited' && current >= cap) {
    // Cap hit — return 403 + offer queue option (client-side decides via secondary CTA)
    return res.status(403).json({
      error: 'Tier cap reached: pdf_send_cap',
      code: 'tier_gate_exceeded',
      gate_id: 'pdf_send_cap',
      current_tier: ent.tier,
      limit: cap, current,
      can_queue_for_next_month: true,
      next_reset_date: nextMonthFirstDay().toISOString(),
    });
  }

  // ... existing send logic
});

// New endpoint — client calls when user taps "Next month: in X days"
const QueueSendBody = z.object({
  invoice_id: z.string().uuid().optional(),
  proposal_id: z.string().uuid().optional(),
}).strict().refine(d => !!(d.invoice_id || d.proposal_id), 'either invoice_id or proposal_id required');

apiRouter.post('/me/queue-pending-send', validateBody(QueueSendBody),
  async (req: AuthenticatedRequest, res) => {
    const { invoice_id, proposal_id } = req.body;
    const sendKind = invoice_id ? 'invoice' : 'proposal';
    const sourceId = invoice_id ?? proposal_id;
    const scheduledFor = nextMonthFirstDay();

    await pg.query(`
      INSERT INTO pending_sends (profile_id, send_kind, source_id, scheduled_for)
      VALUES ($1, $2, $3, $4)
    `, [req.user!.id, sendKind, sourceId, scheduledFor]);

    res.json({ scheduled_for: scheduledFor.toISOString() });
  }
);

function nextMonthFirstDay(): Date {
  const d = new Date();
  return new Date(d.getFullYear(), d.getMonth() + 1, 1, 0, 5, 0); // 00:05 of next month
}
```

### 3.3 Send queue processor cron

```typescript
// backend/src/jobs/sendQueueProcessor.ts
// Runs every 5 minutes, but the actual flushing happens only after monthly counter reset
export async function processSendQueue() {
  const { rows } = await pg.query(`
    SELECT * FROM pending_sends
     WHERE status = 'queued' AND scheduled_for <= NOW()
     ORDER BY scheduled_for ASC
     LIMIT 100
  `);

  for (const send of rows) {
    try {
      // Check if user still qualifies (tier still Open OR they've upgraded — either way, attempt the send)
      const ent = await resolveTier(send.profile_id);
      const isOpenTier = ent.tier === 'open';

      // For Open users: respect the cap that just reset (5/mo)
      const current = await getCurrentPdfSends(send.profile_id);
      if (isOpenTier && current >= 5) {
        // Defer — leave queued for next month
        continue;
      }

      if (send.send_kind === 'invoice') {
        await sendInvoice(send.source_id, isOpenTier);
      } else {
        await sendProposal(send.source_id, isOpenTier);
      }

      await pg.query(`UPDATE pending_sends SET status='sent', updated_at=NOW() WHERE id=$1`, [send.id]);

      // Counter increment
      await pg.query(`UPDATE profiles SET pdf_sends_this_month = pdf_sends_this_month + 1 WHERE id=$1`, [send.profile_id]);

      // Notify user via FCM
      await sendPush(send.profile_id, {
        title: 'Queued send delivered',
        body: `Your ${send.send_kind} was sent.`,
      });
    } catch (e: any) {
      const attempts = send.attempts + 1;
      const status = attempts >= 3 ? 'failed' : 'queued';
      await pg.query(`
        UPDATE pending_sends SET attempts=$2, status=$3, last_error=$4, updated_at=NOW()
         WHERE id=$1
      `, [send.id, attempts, status, e.message]);
      console.error('[send-queue] failed', send.id, e);
    }
  }
}

cron.schedule('*/5 * * * *', processSendQueue);
```

### 3.4 Endpoint to list/cancel pending sends (user can change their mind)

```typescript
apiRouter.get('/me/pending-sends', async (req: AuthenticatedRequest, res) => {
  const { rows } = await pg.query(`
    SELECT * FROM pending_sends WHERE profile_id=$1 AND status='queued' ORDER BY scheduled_for ASC
  `, [req.user!.id]);
  res.json({ pending_sends: rows });
});

apiRouter.delete('/me/pending-sends/:id', async (req: AuthenticatedRequest, res) => {
  await pg.query(`UPDATE pending_sends SET status='canceled' WHERE id=$1 AND profile_id=$2`,
    [req.params.id, req.user!.id]);
  res.status(204).end();
});
```

## 4. Acceptance criteria

| AC | Description |
|---|---|
| AC-1 | Open user hits 6th send → 403 includes `can_queue_for_next_month: true` and `next_reset_date` |
| AC-2 | POST /api/me/queue-pending-send creates a pending_sends row with scheduled_for = next month day-1 00:05 |
| AC-3 | Send queue processor runs every 5 min, picks up queued sends with scheduled_for <= NOW() |
| AC-4 | After monthly counter reset (F6.1) on day 1, cron flushes queued sends respecting 5/mo cap |
| AC-5 | Successful flush increments pdf_sends_this_month counter |
| AC-6 | Failed send increments attempts; after 3, status='failed' |
| AC-7 | If user upgraded to Solo before flush, queued send still fires (no cap to hit) |
| AC-8 | If queue depth > 5 for a user still on Open, only 5 flush; rest stay queued for following month |
| AC-9 | User can list pending sends via GET /api/me/pending-sends |
| AC-10 | User can cancel pending send via DELETE /api/me/pending-sends/:id |
| AC-11 | Branding decision at queue-flush time (per F8.1) |

## 5. BDD scenarios

```gherkin
Scenario: User queues over-cap send
  Given a Free user with 5 sends already this month
  When they POST /api/invoices/:id/send
  Then the response is 403 with can_queue_for_next_month: true
  When they POST /api/me/queue-pending-send { invoice_id }
  Then a pending_sends row is created with scheduled_for next month 00:05

Scenario: Cron flushes queue after monthly reset
  Given a queued pending send with scheduled_for in the past (day 1 of new month)
  And the user is still Open with 0 sends this month
  When sendQueueProcessor cron runs
  Then the send executes (with branding per F8.1)
  And pending_sends.status = 'sent'
  And profiles.pdf_sends_this_month = 1
  And user receives FCM notification

Scenario: User cancels a pending send
  Given a queued pending_sends row
  When DELETE /api/me/pending-sends/:id is called
  Then status becomes 'canceled'
  And cron skips it on next run

Scenario: User upgrades to Solo before flush
  Given a queued send for a user
  And the user upgrades to Solo before the cron fires
  When cron processes the queue
  Then the send fires immediately (no cap to respect)
  And the send goes WITHOUT branding (per F8.1 tier-at-send-time rule)
```

## 6. Edge cases

| Case | Behavior |
|---|---|
| Underlying invoice deleted before flush | cron catches missing source; marks failed; logs |
| User account deleted | ON DELETE CASCADE removes pending_sends |
| Cron stops for days | Backlog flushes in next run; LIMIT 100 paginates |
| Queue grows > 100 for single user | Each cron run drains 100; eventually catches up; alert if > 1000 |
