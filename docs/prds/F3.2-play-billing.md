# F3.2 — Play Billing client + server verification

| Field | Value |
|---|---|
| Pitch | 3 — Stripe + Play Billing |
| Cycle | 2 |
| Appetite | 6 days |
| Owner | Android + backend |
| Dependencies | F2.1, F2.2, F3.1 (subscriptions table + reconcile patterns) |
| Closes blocker | B2 (Android part), S10 (Critical) |

---

## 1. Problem

Play Store policy requires in-app purchases to use Play Billing. Stripe alone is not allowed for digital subscriptions on Android. Need: client-side BillingClient + server-side purchase token verification + RTDN (Real-Time Developer Notifications) handling.

## 2. Goal

After this PRD: Android user can:
- Tap "Upgrade to Solo" in N7 pricing screen → Play Billing flow
- Purchase token sent to server → verified via Google Play Developer API → subscriptions row created
- Renewal events from RTDN webhook update subscription state
- Acknowledge purchase server-side within 3 days (Play requirement)

## 3. Non-goals

- Stripe (F3.1)
- Subscription reconciler (F3.3)
- The Android UI itself (F4.3 TierPricingScreen)
- iOS App Store IAP (out of scope v1)

## 4. Design

### 4.1 Play Console product setup (one-time, documented in `docs/ops/PLAY-PRODUCTS.md`)

In Play Console → Monetize → Subscriptions:
- Subscription IDs: `sub_solo_monthly`, `sub_solo_annual`, `sub_advanced_monthly`, `sub_advanced_annual`, `sub_enterprise_monthly`, `sub_enterprise_annual`
- Pricing per region (USD baseline; Play auto-localizes)
- Free trial offers configured per subscription where applicable
- RTDN topic configured (Pub/Sub) → subscription endpoint pointed at our `/webhooks/play-billing`

### 4.2 Android: BillingClient integration

```kotlin
// android/app/src/main/java/com/guildofsmiths/trademesh/billing/BillingService.kt
object BillingService {
    private lateinit var billingClient: BillingClient

    fun init(context: Context, onPurchases: (List<Purchase>) -> Unit) {
        billingClient = BillingClient.newBuilder(context)
            .setListener { _, purchases -> purchases?.let(onPurchases) }
            .enablePendingPurchases()
            .build()
        billingClient.startConnection(object : BillingClientStateListener {
            override fun onBillingSetupFinished(result: BillingResult) { /* ready */ }
            override fun onBillingServiceDisconnected() { /* retry on next attempt */ }
        })
    }

    suspend fun querySubscriptions(): List<ProductDetails> {
        val params = QueryProductDetailsParams.newBuilder()
            .setProductList(listOf(
                product("sub_solo_monthly"),
                product("sub_solo_annual"),
                product("sub_advanced_monthly"),
                product("sub_advanced_annual"),
                product("sub_enterprise_monthly"),
                product("sub_enterprise_annual"),
            ))
            .build()
        return billingClient.queryProductDetails(params).productDetailsList ?: emptyList()
    }

    fun launchPurchase(activity: Activity, productDetails: ProductDetails, offerToken: String) {
        val flowParams = BillingFlowParams.newBuilder()
            .setProductDetailsParamsList(listOf(
                BillingFlowParams.ProductDetailsParams.newBuilder()
                    .setProductDetails(productDetails)
                    .setOfferToken(offerToken)
                    .build()
            ))
            .build()
        billingClient.launchBillingFlow(activity, flowParams)
    }

    suspend fun acknowledge(purchaseToken: String) {
        if (billingClient.connectionState != BillingClient.ConnectionState.CONNECTED) return
        val params = AcknowledgePurchaseParams.newBuilder().setPurchaseToken(purchaseToken).build()
        billingClient.acknowledgePurchase(params)
    }

    private fun product(id: String) = QueryProductDetailsParams.Product.newBuilder()
        .setProductId(id)
        .setProductType(BillingClient.ProductType.SUBS)
        .build()
}
```

After `onPurchases` fires:
1. POST purchase token to backend `/api/me/upgrade-play`
2. On 200 response, call `acknowledge(token)` (server already did server-side ack — client-side ack is also required by some flows)

### 4.3 Server: purchase verification endpoint

```typescript
// POST /api/me/upgrade-play
const UpgradePlayBody = z.object({
  productId: z.string().min(1),
  purchaseToken: z.string().min(1),
}).strict();

apiRouter.post('/me/upgrade-play', requireVerifiedEmail, validateBody(UpgradePlayBody),
  async (req: AuthenticatedRequest, res) => {
    const { productId, purchaseToken } = req.body;
    const profileId = req.user!.id;

    // Verify with Google Play Developer API
    const verification = await playDeveloperApi.purchases.subscriptions.get({
      packageName: 'com.guildofsmiths.trademesh',
      subscriptionId: productId,
      token: purchaseToken,
    });

    if (verification.data.purchaseState !== 0) { // 0 = Purchased
      return res.status(400).json({ error: 'purchase_not_active' });
    }

    // Map productId → tier + cadence
    const { tier, cadence } = mapProductIdToTier(productId);
    const expiryMs = Number(verification.data.expiryTimeMillis);

    // Insert/update subscriptions
    await pg.query(`
      INSERT INTO subscriptions
        (profile_id, tier, cadence, provider, provider_subscription_id,
         status, current_period_start, current_period_end, cents_per_period)
      VALUES ($1, $2, $3, 'play_billing', $4,
              'active', NOW(), to_timestamp($5/1000.0), $6)
      ON CONFLICT (provider, provider_subscription_id) DO UPDATE
        SET status='active', current_period_end=EXCLUDED.current_period_end, updated_at=NOW()
    `, [profileId, tier, cadence, purchaseToken, expiryMs, centsForProductId(productId)]);

    // Update profile.tier
    await pg.query(`UPDATE profiles SET tier=$2 WHERE id=$1`, [profileId, tier]);

    // Server-side acknowledge (must happen within 3 days per Play policy)
    if (verification.data.acknowledgementState === 0) { // not yet acknowledged
      await playDeveloperApi.purchases.subscriptions.acknowledge({
        packageName: 'com.guildofsmiths.trademesh',
        subscriptionId: productId,
        token: purchaseToken,
      });
    }

    await emit('tier_upgrade.paid_converted', profileId, tier);

    res.status(200).json({ tier, expiryMs });
  }
);
```

### 4.4 RTDN webhook

```typescript
// POST /webhooks/play-billing — UNAUTHENTICATED, signature-verified via JWT in body
app.post('/webhooks/play-billing', async (req, res) => {
  // RTDN sends a Pub/Sub message; verify JWT from message authentication
  // ...verification via google-auth-library...

  const decoded = decodeRtdnMessage(req.body);
  if (!decoded) return res.status(400).end();

  // Idempotency
  const messageId = decoded.message.messageId;
  const { rows: existing } = await pg.query(
    `SELECT id FROM provider_webhook_events WHERE id = $1`, [messageId]
  );
  if (existing.length > 0) return res.status(200).end();

  await pg.query(`
    INSERT INTO provider_webhook_events (id, provider, event_type, payload)
    VALUES ($1, 'play_billing', $2, $3::jsonb)
  `, [messageId, decoded.notificationType, JSON.stringify(decoded)]);

  // Process notification types
  switch (decoded.notificationType) {
    case 'SUBSCRIPTION_RENEWED':
    case 'SUBSCRIPTION_RECOVERED':
      await playRenewSubscription(decoded);
      break;
    case 'SUBSCRIPTION_CANCELED':
    case 'SUBSCRIPTION_EXPIRED':
      await playMarkCanceled(decoded);
      break;
    case 'SUBSCRIPTION_ON_HOLD':
    case 'SUBSCRIPTION_IN_GRACE_PERIOD':
      await playMarkPastDue(decoded);
      break;
    // ... other types ...
  }

  await pg.query(`UPDATE provider_webhook_events SET processed_at=NOW() WHERE id=$1`, [messageId]);
  res.status(200).end();
});
```

## 6. BDD scenarios

```gherkin
Feature: Play Billing for Android subscriptions

Scenario: User purchases Solo monthly via Play
  Given a verified Open user on Android
  When they tap "Upgrade to Solo" in N7
  And BillingService.launchPurchase opens Play
  And user completes purchase
  Then onPurchases fires with the Purchase
  When client POSTs /api/me/upgrade-play with productId="sub_solo_monthly" and purchaseToken
  Then server verifies via Google Play Developer API → purchaseState=0
  And subscriptions row inserted with tier="solo", provider="play_billing"
  And profile.tier becomes "solo"
  And server acknowledges the purchase
  And client also acknowledges
  And telemetry "tier_upgrade.paid_converted" fires

Scenario: Renewal handled via RTDN
  Given an active Play Billing solo subscription
  When SUBSCRIPTION_RENEWED RTDN message arrives
  Then subscriptions.current_period_end is extended
  And status remains "active"

Scenario: Subscription expired
  Given an active subscription whose period ended
  When SUBSCRIPTION_EXPIRED RTDN arrives
  Then subscriptions.status becomes "expired"
  And tier downgrade is handled by F7.1 cron

Scenario: Forged purchase token rejected
  When POST /api/me/upgrade-play with random fake purchaseToken
  Then Google Play Developer API returns 4xx
  And our server returns 400
  And no subscription is created
```

## 7. Edge cases

| Case | Behavior |
|---|---|
| Network failure during verify | Server retries via 503; client retries; final fallback: reconciler cron (F3.3) catches the purchase later |
| User restores purchase on new device | BillingClient.queryPurchases returns existing; client calls /api/me/upgrade-play to re-link |
| Acknowledge fails (server down) | Client retries acknowledge; if not done within 3 days, Play refunds — bug to monitor |
| User upgrades from Solo → Advanced via Play | New purchaseToken; old subscription marked canceled via RTDN; new one created |
| Sandbox test purchases | Tagged via `verification.purchaseType === 0` (test) — log but do not record real revenue |
