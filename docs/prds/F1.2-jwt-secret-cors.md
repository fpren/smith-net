## 1. Problem

`backend/src/auth.ts` line 21:

```typescript
const JWT_SECRET = process.env.JWT_SECRET || 'smith-net-dev-secret-change-in-production';
```

This means a production deploy missing `JWT_SECRET` env var **silently uses a known-published secret** — anyone reading the GitHub repo can forge tokens.

Additionally, `backend/src/server.ts`:

```typescript
app.use(cors({ origin: '*', methods: [...], allowedHeaders: [...] }));
```

CORS is wide-open. Any website can call our API from a browser.

## 2. Goal

After this PRD:
- Production refuses to start if JWT_SECRET is unset OR equals the dev fallback string
- CORS allowlist locked to known mobile + desktop portal origins
- Secret-rotation procedure documented

## 3. Non-goals

- Migrating to a secrets manager (S14) — that's a follow-up PRD
- Rotating the existing dev secret — dev / staging already use env-supplied secrets
- Adding signed cookies / SameSite enforcement — JWT in Authorization header is the model

## 4. Design

### 4.1 JWT secret hard-fail

```typescript
// backend/src/auth.ts
const DEV_FALLBACK = 'smith-net-dev-secret-change-in-production';
const JWT_SECRET = process.env.JWT_SECRET;

if (!JWT_SECRET) {
  throw new Error('[FATAL] JWT_SECRET env var is required');
}
if (JWT_SECRET === DEV_FALLBACK && process.env.NODE_ENV === 'production') {
  throw new Error('[FATAL] JWT_SECRET is set to the dev fallback in production. Set a real secret.');
}
if (JWT_SECRET.length < 32) {
  throw new Error(`[FATAL] JWT_SECRET must be at least 32 characters (got ${JWT_SECRET.length})`);
}

export { JWT_SECRET };
```

In dev (`NODE_ENV=development` or unset), allow short secrets and the literal dev fallback so local devs aren't blocked.

### 4.2 Token refresh secret

If `REFRESH_SECRET` is currently `JWT_SECRET`, split them:

```typescript
const REFRESH_SECRET = process.env.JWT_REFRESH_SECRET || JWT_SECRET;
```

Same hard-fail logic if `JWT_REFRESH_SECRET` is set but invalid.

### 4.3 CORS allowlist

```typescript
// backend/src/server.ts
const ALLOWED_ORIGINS = [
  /^https:\/\/portal\.smithnet\.app$/,
  /^https:\/\/smithnet\.app$/,
  /^https:\/\/.*\.smithnet\.app$/, // staging subdomains
  /^smithnet:\/\//,                  // Android scheme (custom URI)
];

if (process.env.NODE_ENV === 'development') {
  ALLOWED_ORIGINS.push(/^http:\/\/localhost(:\d+)?$/);
  ALLOWED_ORIGINS.push(/^http:\/\/192\.168\.\d+\.\d+(:\d+)?$/); // for device-on-LAN dev
}

app.use(cors({
  origin: (origin, cb) => {
    // Allow no-origin requests (mobile apps, curl)
    if (!origin) return cb(null, true);
    if (ALLOWED_ORIGINS.some(r => r.test(origin))) {
      return cb(null, true);
    }
    return cb(new Error('CORS: origin not allowed'));
  },
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
  allowedHeaders: ['Content-Type', 'Authorization'],
}));
```

Note: removed `X-User-Id` and `X-User-Name` from `allowedHeaders` (per F1.1).

### 4.4 Secret rotation procedure (documented in `docs/ops/SECRETS.md` — new file)

```
JWT secret rotation procedure:

1. Generate new secret: openssl rand -hex 32
2. Update production env JWT_SECRET_NEXT
3. Modify auth.ts to verify with both JWT_SECRET and JWT_SECRET_NEXT for grace window
4. Wait one access-token TTL (7 days) — all in-flight tokens expire
5. Promote: JWT_SECRET = old JWT_SECRET_NEXT; remove old
6. Confirm clean log of any "rejected on old secret" entries
```

```gherkin

  Given NODE_ENV=production
  And JWT_SECRET="smith-net-dev-secret-change-in-production"

  And the process exits non-zero

Scenario: Short JWT_SECRET fails boot in any env
  Given JWT_SECRET="short"
  And NODE_ENV=production (or any)
  When the backend starts
  Then it logs FATAL must be at least 32 characters
  And the process exits non-zero

Scenario: Dev env accepts short secret
  Given NODE_ENV=development
  And JWT_SECRET="dev-secret"
  When the backend starts
  Then it boots successfully

Feature: CORS lockdown

Scenario: Allowed origin can preflight
  When OPTIONS /api/jobs arrives with Origin: https://portal.smithnet.app
  Then the response is 204 with Access-Control-Allow-Origin: https://portal.smithnet.app

Scenario: Disallowed origin is rejected
  When OPTIONS /api/jobs arrives with Origin: https://evil.com
  Then the response does NOT include Access-Control-Allow-Origin
  And the browser blocks the request

Scenario: Mobile app (no Origin header) is allowed
  When POST /api/jobs arrives with no Origin header
  And valid Authorization
  Then the response is 200 (not blocked by CORS)

Scenario: Local dev origin is allowed
  Given NODE_ENV=development
  When OPTIONS /api/jobs arrives with Origin: http://localhost:5173
  Then the response is 204 with the matching Allow-Origin header
```

## 8. Edge cases

| Case | Behavior |
|---|---|
| `NODE_ENV` unset | Treat as production (fail-safe) |
| Origin header sent as empty string `""` | Allowed (browsers behavior) — per `if (!origin)` check |
| `Vary: Origin` header missing | Add `app.set('etag', false)` if needed; CORS middleware auto-handles |
| Allowed-list update requires deploy | Acceptable trade-off — origins shouldn't change frequently; a future migration could load from env |
| Webhook routes called from Stripe / Play | Webhook routes will be in `/webhooks/*` (not `/api/*`) — applied separately in F3.1 with their own auth (signature verification) |
