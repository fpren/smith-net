## 1. Problem

`SUCCESS-METRICS.md §gate-event-taxonomy` defines 10+ telemetry events that the funnel + tier-gate analytics depend on. No sink exists. No PII allowed.

## 2. Goal

After this PRD: a server-authoritative table receives telemetry events with hashed user IDs, queryable for funnel + cohort analysis. Client and server can both emit.

## 3. Non-goals

- Real-time dashboards (query offline v1)
- Stream processing / Kafka — direct DB inserts
- Cross-event correlation in DB — exported to a query tool later

## 4. Design

### 4.1 Migration M4

```sql
-- 008_create_gate_hit_events_table.sql
BEGIN;

CREATE TABLE IF NOT EXISTS gate_hit_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event TEXT NOT NULL,
  user_id_hash TEXT NOT NULL,         -- SHA256(profile.id) — no PII
  current_tier TEXT NOT NULL,
  metadata JSONB NOT NULL DEFAULT '{}',
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_gate_hit_events_event ON gate_hit_events(event, occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_gate_hit_events_user_hash ON gate_hit_events(user_id_hash, occurred_at DESC);

COMMIT;
```

### 4.2 Service

```typescript
// backend/src/services/telemetry.ts
import crypto from 'crypto';
import { pg } from '../db';
import { Tier } from '../types/tier';

export const ALLOWED_EVENTS = new Set([
  'gate_hit.active_job_cap',
  'gate_hit.pdf_send_cap',
  'gate_hit.plan_compiler_preview',
  'gate_hit.plan_compiler_preview_dismissed',
  'gate_hit.ai_tab',
  'gate_hit.crew_invite',
  'tier_upgrade.cta_shown',
  'tier_upgrade.cta_clicked',
  'tier_upgrade.cta_dismissed',
  'tier_upgrade.trial_started',
  'tier_upgrade.trial_expired',
  'tier_upgrade.paid_converted',
  'tier_downgrade.canceled',
  'funnel.signup',
  'funnel.first_invoice_sent',
]);

const PII_KEYS = ['email', 'name', 'phone', 'address', 'profile_id', 'userId'];

export async function emit(event: string, profileId: string, currentTier: Tier, metadata: Record<string, unknown> = {}) {
  if (!ALLOWED_EVENTS.has(event)) {
    console.warn('[telemetry] unknown event', event);
    return;
  }
  // Sanitize PII
  const cleanMeta = Object.fromEntries(
    Object.entries(metadata).filter(([k]) => !PII_KEYS.includes(k))
  );
  const userIdHash = crypto.createHash('sha256').update(profileId).digest('hex');
  await pg.query(
    `INSERT INTO gate_hit_events (event, user_id_hash, current_tier, metadata)
     VALUES ($1, $2, $3, $4::jsonb)`,
    [event, userIdHash, currentTier, JSON.stringify(cleanMeta)]
  );
}
```

### 4.3 Endpoint (client → server)

```typescript
// POST /api/telemetry/gate-hit
import { z } from 'zod';
import { validateBody } from './middleware/validate';

const TelemetryBody = z.object({
  event: z.enum([...ALLOWED_EVENTS] as [string, ...string[]]),
  metadata: z.record(z.any()).optional(),
}).strict();

apiRouter.post('/telemetry/gate-hit', validateBody(TelemetryBody), async (req: AuthenticatedRequest, res) => {
  const { event, metadata } = req.body;
  await emit(event, req.user!.id, req.user!.tier as Tier, metadata || {});
  res.status(204).end();
});
```

### 4.4 Server-side emitters

Wherever a 403 `tier_gate_exceeded` is returned (F6.1), call `emit()` server-side too — don't trust the client to report. Examples:
- POST /api/jobs cap-hit → `emit('gate_hit.active_job_cap', ...)`
- POST /api/invoices/:id/send cap-hit → `emit('gate_hit.pdf_send_cap', ...)`
- POST /api/me/start-trial success → `emit('tier_upgrade.trial_started', ...)`

## 5. Acceptance criteria

| AC | Description | Verification |
|---|---|---|
| AC-1 | M4 migration runs idempotently | Migration test |
| AC-2 | `emit()` writes a row with hashed user_id_hash | DB assertion |
| AC-3 | `emit()` rejects unknown event names (warn-only, no insert) | Unit test |
| AC-4 | PII fields in metadata are stripped before insert | Sanitizer test |
| AC-5 | POST /api/telemetry/gate-hit requires auth + zod validation | API test |
| AC-6 | Server-side emit called wherever 403 tier_gate_exceeded fires (verified after F6.1) | Cross-PRD integration |
| AC-7 | Inserts are sub-50ms p95 | Perf test |
| AC-8 | `gate_hit_events.user_id_hash` is the same SHA256 across requests for same profile | Determinism |

## 6. BDD scenarios

```gherkin
Feature: Telemetry sink

Scenario: Client emits a gate-hit event
  Given an authenticated user
  When POST /api/telemetry/gate-hit with body {"event":"gate_hit.ai_tab"}
  Then the response is 204
  And a row exists in gate_hit_events with event="gate_hit.ai_tab"
  And user_id_hash equals SHA256(profile.id)
  And current_tier matches the user's JWT tier

Scenario: Unknown event names rejected by zod
  When POST /api/telemetry/gate-hit with {"event":"hack.exfiltrate"}
  Then the response is 400 validation
  And no row is inserted

Scenario: PII stripped from metadata
  When emit('gate_hit.ai_tab', 'p123', 'solo', {email: 'a@b.com', screenName: 'AI'})
  Then the inserted row has metadata = {"screenName":"AI"}
  And does NOT contain email

Scenario: Server-side emit on 403
  Given a Free user
  When POST /api/jobs returns 403 active_job_cap
  Then a gate_hit_events row exists with event="gate_hit.active_job_cap"
  Even if the client never POSTs to /api/telemetry/gate-hit
```

## 7. Edge cases

| Case | Behavior |
|---|---|
| Telemetry endpoint flooded by abusive client | Rate-limited per-user (60/min) on top of global limit |
| `gate_hit_events` table grows unbounded | Retention cron (90 days) — separate PRD F11.1 generalizes this |
| Event emitted before user authenticates | Server endpoint requires auth; pre-auth events not collected v1 |
| Hash collision (SHA256 truncated?) | Use full 64-hex SHA256; collision space negligible |
