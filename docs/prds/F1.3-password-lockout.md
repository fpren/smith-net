# F1.3 — Password floor + per-account lockout

| Field | Value |
|---|---|
| Pitch | 1 — Auth security hardening |
| Cycle | 1 |
| Appetite | 3 days |
| Owner | backend |
| Dependencies | F1.1 (auth middleware), F1.2 (JWT secret) |
| Closes blocker | S5 |

---

## 1. Problem

`auth.ts` currently allows passwords ≥ 6 chars. There's no per-account lockout — only an IP-based rate limit (20 reqs / 15min on `/api/auth/*`). A determined attacker can credential-stuff against many accounts from a botnet.

## 2. Goal

After this PRD:
- Min password length = 8 chars
- Required: at least one digit AND at least one letter
- Per-account lockout: 5 consecutive failed logins → 15-min cooldown
- Existing users with shorter passwords are NOT forced to reset (grandfathered) — only new passwords / changes enforce

## 3. Non-goals

- Password complexity beyond digit+letter (no symbol requirement — friction without benefit at this stage)
- Password rotation requirement (proven counter-productive — NIST 800-63B)
- Forcing existing users to upgrade — out of scope
- Password reset email flow (already exists; untouched)

## 4. Design

### 4.1 Password validator

```typescript
// backend/src/auth.ts
const MIN_PASSWORD_LENGTH = 8;

function validatePassword(password: string): { valid: true } | { valid: false; reason: string } {
  if (password.length < MIN_PASSWORD_LENGTH) {
    return { valid: false, reason: `Password must be at least ${MIN_PASSWORD_LENGTH} characters` };
  }
  if (!/[a-zA-Z]/.test(password)) {
    return { valid: false, reason: 'Password must contain at least one letter' };
  }
  if (!/[0-9]/.test(password)) {
    return { valid: false, reason: 'Password must contain at least one digit' };
  }
  return { valid: true };
}
```

Apply at:
- `userStore.createUser()` (registration)
- Password change endpoint (if exists; else add when user-profile updates exposed)
- NOT on `userStore.verifyPassword()` — login uses existing password as-is

### 4.2 Lockout schema

Migration `add_account_lockout_columns_to_profiles.sql`:

```sql
ALTER TABLE profiles
  ADD COLUMN IF NOT EXISTS failed_login_count INTEGER NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS locked_until TIMESTAMPTZ;
```

### 4.3 Lockout enforcement

```typescript
// backend/src/authRoutes.ts (login handler)
authRouter.post('/login', async (req, res) => {
  const { email, password } = req.body;
  // ... existing validation ...

  const profile = await userStore.findByEmail(email);
  if (!profile) {
    auditLog.log(AuditAction.USER_LOGIN_FAILED, 'unknown', { email, reason: 'no_account' });
    // Constant-time delay to avoid email enumeration
    await sleep(200);
    return res.status(401).json({ error: 'Invalid credentials' });
  }

  // Lockout check
  if (profile.locked_until && new Date(profile.locked_until) > new Date()) {
    auditLog.log(AuditAction.USER_LOGIN_FAILED, profile.id, { reason: 'locked' });
    const minutesRemaining = Math.ceil((profile.locked_until.getTime() - Date.now()) / 60000);
    return res.status(429).json({
      error: 'Account temporarily locked',
      code: 'account_locked',
      retry_after_minutes: minutesRemaining,
    });
  }

  // Verify password
  const valid = await userStore.verifyPasswordWithHash(password, profile.password_hash);
  if (!valid) {
    const newCount = (profile.failed_login_count || 0) + 1;
    const updates: Record<string, any> = { failed_login_count: newCount };
    if (newCount >= 5) {
      updates.locked_until = new Date(Date.now() + 15 * 60 * 1000); // 15 min
      auditLog.log(AuditAction.SECURITY_ALERT, profile.id, { reason: 'lockout_triggered' });
    }
    await userStore.updateProfile(profile.id, updates);
    auditLog.log(AuditAction.USER_LOGIN_FAILED, profile.id, { fail_count: newCount });
    return res.status(401).json({ error: 'Invalid credentials' });
  }

  // Successful login — reset counter
  if (profile.failed_login_count > 0) {
    await userStore.updateProfile(profile.id, { failed_login_count: 0, locked_until: null });
  }
  // ... existing token generation ...
});
```

### 4.4 Constant-time email enumeration defense

The 200ms `sleep()` after "no account" path matches the bcrypt verify time (cost 10 ≈ 70-200ms). This prevents timing-based account enumeration.

### 4.5 Registration validator

```typescript
authRouter.post('/register', async (req, res) => {
  const { email, password, displayName } = req.body;

  if (!email || !password || !displayName) {
    return res.status(400).json({ error: 'Email, password, and displayName are required' });
  }

  const passwordValidation = validatePassword(password);
  if (!passwordValidation.valid) {
    return res.status(400).json({ error: passwordValidation.reason, code: 'weak_password' });
  }

  // ... existing user creation ...
});
```

## 5. Acceptance criteria

| AC | Description | Verification |
|---|---|---|
| AC-1 | Registration with password "abc123" (6 chars, has letter+digit) → 400 with reason | API test |
| AC-2 | Registration with password "abcdefgh" (8 chars, no digit) → 400 | API test |
| AC-3 | Registration with password "password" (8 chars, no digit) → 400 | API test |
| AC-4 | Registration with password "Pass1234" → 201 success | API test |
| AC-5 | 5 wrong-password attempts on same account → 6th returns 429 with `account_locked`, retry_after_minutes | API test |
| AC-6 | After 15 minutes, lockout clears and login succeeds with correct password | Time-travel test |
| AC-7 | Successful login resets failed_login_count to 0 | DB assertion |
| AC-8 | Failed login on non-existent email returns 401 (not 404 — no enumeration) within ~200ms timing window | Timing test |
| AC-9 | Audit log records `USER_LOGIN_FAILED` with `fail_count` for each fail | Log assertion |
| AC-10 | Audit log records `SECURITY_ALERT` with `reason: lockout_triggered` on 5th fail | Log assertion |
| AC-11 | Existing users with passwords < 8 chars can still log in (grandfathered) | Regression test |

  Given a user "alice" with correct password "Correct1"
  When POST /api/auth/login fails 5 times in succession with wrong passwords

  And the response includes retry_after_minutes
  And profiles.locked_until is set to NOW() + 15 minutes

Scenario: Lockout clears after 15 minutes
  Given alice's account is locked with locked_until in the past
  When POST /api/auth/login arrives with correct password
  Then the response is 200 with valid tokens
  And failed_login_count resets to 0
  And locked_until is cleared

Scenario: Email enumeration timing attack defended
  When POST /api/auth/login with email "nonexistent@example.com" and any password
  Then the response time is within 50ms of typical bcrypt verify time (200ms)
  And the response is 401 (not 404 — same as wrong-password)

Scenario: Existing user with weak password grandfathered
  Given alice registered before this PRD with password "weak6"
  When POST /api/auth/login with email and "weak6"
  Then the response is 200 (login succeeds)
  But she may receive a one-time prompt on next session to change to a stronger password (not blocking)

## 7. Edge cases

| Case | Behavior |
|---|---|
| User changes their own password to weak | 400 reject with reason |
| Admin force-resets user's password (via /api/admin/reset) | Same validator runs; admin must supply strong password |
| Concurrent failed logins (race) | Postgres UPDATE counter atomic; safe |
| Distributed timing attack via many IPs hitting same account | Lockout fires after 5 attempts regardless of IP — by design |
| Lockout clear time stale in cache | `locked_until` is server-authoritative; no caching |

## 10. Risk

| Risk | Mitigation |
|---|---|
| Legitimate user fat-fingers 5 times → locked out | 15-min cooldown is brief; user can also request password reset (existing flow) |
| Attacker uses lockout as DoS by spamming wrong passwords on victim's account | 15-min lockout is acceptable — attacker can't abuse this beyond annoyance; tracked in alerts |
| Existing users w/ weak passwords have lower security | Grandfathered intentionally — forced reset is friction; consider "improve your password" prompt later |
