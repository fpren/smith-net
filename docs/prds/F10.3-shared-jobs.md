# F10.3 — Shared jobs across crew (org_id on jobs)

| Field | Value |
|---|---|
| Pitch | 10 — Crew + dispatch |
| Cycle | 5 |
| Appetite | 4 days |
| Owner | backend + Android |
| Dependencies | F10.1 (orgs), F10.2 (crew membership) |

---

## 1. Problem

Existing `jobs.created_by` scopes to single user. For Enterprise crew, jobs need to be visible across crew members of the same org with role-based visibility.

## 2. Goal

After this PRD: jobs created by any crew member are visible to others in the same org. Existing solo `created_by` filter remains for non-Enterprise users. Server enforces; clients see appropriate subset.

## 3. Non-goals

- Per-job sharing rules (all org-scoped jobs visible to all members)
- Cross-org collaboration
- Read/write granularity (all members can edit; foreman+ can delete)

## 4. Design

### 4.1 Migration

```sql
-- 018_add_org_id_to_jobs.sql
ALTER TABLE jobs ADD COLUMN IF NOT EXISTS org_id UUID REFERENCES organizations(id);
CREATE INDEX IF NOT EXISTS idx_jobs_org ON jobs(org_id) WHERE org_id IS NOT NULL;

-- Backfill: set org_id for existing jobs based on creator's primary org (if any)
UPDATE jobs SET org_id = p.org_id
  FROM profiles p
 WHERE jobs.created_by = p.id AND p.org_id IS NOT NULL
   AND jobs.org_id IS NULL;
```

(Same `org_id` migration applied to: `time_entries`, `materials`, `intents`, `proposals`, `invoices`, `reports` — all entities that should be crew-shared.)

### 4.2 Server query update

Helper:

```typescript
// backend/src/services/visibilityScope.ts
export async function buildJobVisibilityClause(profileId: string): Promise<{ clause: string; params: any[] }> {
  const { rows } = await pg.query(`SELECT org_id FROM profiles WHERE id = $1`, [profileId]);
  const orgId = rows[0]?.org_id;
  if (orgId) {
    // Crew member: see jobs created_by self OR org_id = my org
    return {
      clause: `(created_by = $1 OR org_id = $2)`,
      params: [profileId, orgId],
    };
  }
  // Solo: see only own jobs
  return {
    clause: `created_by = $1`,
    params: [profileId],
  };
}
```

Apply to GET /api/jobs:

```typescript
apiRouter.get('/jobs', async (req: AuthenticatedRequest, res) => {
  const scope = await buildJobVisibilityClause(req.user!.id);
  const { rows } = await pg.query(
    `SELECT * FROM jobs WHERE ${scope.clause} ORDER BY updated_at DESC LIMIT 200`,
    scope.params
  );
  res.json({ jobs: rows });
});
```

Apply same pattern to GET endpoints for time_entries, materials, intents, proposals, invoices, reports.

### 4.3 Job creation auto-tags org_id


### 4.4 Edit / delete authorization

```typescript
async function canEditJob(jobId: string, profileId: string): Promise<boolean> {
  const { rows } = await pg.query(`SELECT created_by, org_id FROM jobs WHERE id = $1`, [jobId]);
  if (rows.length === 0) return false;
  const job = rows[0];
  if (job.created_by === profileId) return true;
  // Crew member from same org
  if (job.org_id) {
    const { rows: m } = await pg.query(
      `SELECT 1 FROM org_members om JOIN profiles p ON p.id = $1
        WHERE p.org_id = om.org_id AND om.profile_id = $1
          AND om.org_id = $2 AND om.removed_at IS NULL`,
      [profileId, job.org_id]
    );
    return m.length > 0;
  }
  return false;
}

async function canDeleteJob(jobId: string, profileId: string): Promise<boolean> {
  const { rows } = await pg.query(`SELECT created_by, org_id FROM jobs WHERE id = $1`, [jobId]);
  const job = rows[0];
  if (job.created_by === profileId) return true;
  // Foreman+ in same org can delete
  if (job.org_id) {
    const { rows: m } = await pg.query(
      `SELECT role FROM org_members WHERE org_id = $1 AND profile_id = $2 AND removed_at IS NULL`,
      [job.org_id, profileId]
    );
    return m.length > 0 && ['owner', 'foreman'].includes(m[0].role);
  }
  return false;
}
```

Apply to PATCH /api/jobs/:id and DELETE /api/jobs/:id.

### 4.5 Tier-downgrade behavior

When Enterprise expires:
- `subscription_id` becomes NULL on org (per F10.1)
- Crew members can still SEE their own and crew jobs (read-only via `canEditJob` check returning false for all but creator)
- New job creation drops back to solo (`profile.org_id` may be cleared OR retained — decision: **retain** so on re-upgrade, jobs reconnect)
- Active-job cap reapplies: counts only jobs where `created_by = self`

### 4.6 Active-job cap query update

F6.1's `getCurrent` for `activeJobs`:

```typescript
getCurrent: async (req) => {
  // For all tiers: count own active jobs only (not crew jobs)
  const { rows } = await pg.query(
    `SELECT COUNT(*) AS cnt FROM jobs
      WHERE created_by = $1 AND status NOT IN ('done', 'archived')`,
    [req.user!.id]
  );
  return Number(rows[0].cnt);
},
```

(Cap is per-user, not per-org. Solo cap stays meaningful even if user happens to be in an org.)

### 4.7 Android UI

`D1 JobBoardScreen` — for Enterprise users with org, add a CREW column / filter:
- Two filter chips at top: `[ MINE ]` `[ CREW ]` (toggle which subset shown)
- Crew jobs visually tagged with creator initials (badge)
- Existing UI unchanged for solo users (no chips needed)

## 5. Acceptance criteria

| AC | Description |
|---|---|
| AC-1 | Migration adds org_id column to jobs (and parallel entities) |
| AC-2 | Backfill assigns org_id from creator's profile.org_id |
| AC-3 | GET /api/jobs for crew member returns own + org_id-matched jobs |
| AC-4 | GET /api/jobs for solo user returns only own jobs |
| AC-5 | POST /api/jobs auto-sets org_id from profile |
| AC-6 | PATCH /api/jobs/:id: any crew member can edit (canEditJob returns true) |
| AC-7 | DELETE /api/jobs/:id: only creator OR org foreman+/owner can delete |
| AC-8 | Active-job cap counts only `created_by = self` jobs (per-user, not per-org) |
| AC-9 | Enterprise expires → crew jobs read-only for non-creators (canEditJob returns false) |
| AC-10 | Same applied to time_entries, materials, intents, proposals, invoices, reports |
| AC-11 | Android job-board has CREW chip filter for Enterprise users with org; solo users don't see it |

## 6. BDD scenarios

```gherkin
Scenario: Crew member sees fellow member's job
  Given alice and bob are members of the same org
  And alice creates a job
  When bob calls GET /api/jobs
  Then bob receives the job in the response

Scenario: Solo user only sees own jobs
  Given carol is solo (no org)
  And another user dave creates a job
  When carol calls GET /api/jobs
  Then dave's job is NOT in the response

Scenario: Crew member edits crew job
  Given a job created by alice in org X
  When bob (also in org X) calls PATCH /api/jobs/:id
  Then 200 success

Scenario: Crew member cannot delete others' jobs (unless foreman+)
  Given a 'member' role bob attempts DELETE on alice's job in same org
  Then 403 forbidden

Scenario: Foreman can delete crew jobs
  Given foreman role for charlie in org X
  When charlie DELETES alice's job
  Then 200 success

Scenario: Active-job cap stays per-user
  Given a Free-tier user (not in org) with 1 active job
  When they POST /api/jobs
  Then 403 active_job_cap (cap counts their own jobs, not org jobs)

Scenario: Enterprise expires; crew jobs read-only
  Given an org whose subscription expired
  When member bob attempts to PATCH alice's job
  Then 403 forbidden (canEditJob returns false because no active subscription_id)
```

## 7. Edge cases

| Case | Behavior |
|---|---|
| User in two orgs | profile.org_id = primary; secondary org jobs not in default scope (need explicit query) — not v1 UX |
| Job's org_id is set but creator's org_id is now NULL (member removed) | Creator still sees via created_by; org members still see via org_id; intentional — data preservation |
| Org owner deleted | Jobs orphaned; admin reassigns ownership; flagged in F10.1 risk |
| Mass org-id backfill on large existing dataset | Migration acceptable at current scale; 50K jobs runs < 30s |
